# Rate limiter

ограничитель частоты запросов для публичного API. Каждый запрос
приходит от пользователя в некоторый момент времени, и ограничитель сразу
отвечает: пропустить (**A**llow) или отклонить (**D**eny).

Лимиты заданы набором правил вида «не больше `k` запросов за `w`
миллисекунд», например «1 запрос в секунду **и** 10 запросов в минуту».
Запрос пропускается, только если после этого **ни одно** правило не будет
нарушено.

## Правило подсчёта

Для запроса пользователя `u` в момент `t` правило `(k, w)` выполнено, если
число **пропущенных** запросов пользователя `u` с временем в полуинтервале
`(t − w, t]` строго меньше `k`.

- Отклонённые запросы **не** учитываются: пользователь, которого
  отклонили, не «продлевает» себе бан.
- Запрос ровно в момент `t − w` уже вне окна.
- Пользователи независимы друг от друга.
- События идут по неубыванию времени. События с одинаковым временем
  обрабатываются в порядке ввода.

## Формат

**Вход** — одна JSON-строка в stdin:

```json
{"rules": [[k1, w1], [k2, w2]], "users": [u1, u2, ...], "times": [t1, t2, ...]}
```

`users[i]` и `times[i]` описывают `i`-й запрос.

**Выход** — одна JSON-строка в stdout: строка из символов `A`/`D` длины `n`,
где `i`-й символ — решение по `i`-му запросу.

## Ограничения

| Параметр | Значение |
|---|---|
| Количество запросов `n` | 1 ≤ n ≤ 2·10⁵ |
| Количество правил `r` | 1 ≤ r ≤ 3 |
| `k` | 1 ≤ k ≤ 10⁵ |
| `w` | 1 ≤ w ≤ 10¹² |
| Идентификатор пользователя | 0 ≤ u ≤ 10⁹ (разреженные, **не** 0..n) |
| Время | 0 ≤ t ≤ 10¹², неубывающее |
| Время работы | C++ / Rust / Zig — 1 с, Go — 2 с, Python — 5 с |

Обратите внимание: время и окно не помещаются в 32 бита.

## Примеры

**Пример 1.** Правило «2 запроса за 10 мс».

```json
{"rules": [[2, 10]], "users": [1, 1, 1, 2, 1], "times": [0, 5, 9, 9, 10]}
```

```json
"AADAA"
```

- `t=9`, пользователь 1: в окне `(−1, 9]` уже есть пропущенные запросы 0 и 5, отклоняем.
- `t=9`, пользователь 2: у него своя история, пропускаем.
- `t=10`, пользователь 1: окно `(0, 10]`, запрос 0 вышел из окна, остался только 5, пропускаем.

**Пример 2.** Два правила: «1 за 3 мс» и «2 за 10 мс».

```json
{"rules": [[1, 3], [2, 10]], "users": [7, 7, 7, 7, 7, 7], "times": [0, 1, 3, 4, 8, 11]}
```

```json
"ADADDA"
```

- `t=8`: первое правило выполнено (в `(5, 8]` пусто), а второе нет: в `(−2, 8]` уже два пропущенных запроса (0 и 3).
- `t=11`: в `(1, 11]` остался только запрос 3, пропускаем.

## Требование для вашего языка

Решение должно работать за **амортизированное O(1)** на запрос (при
фиксированном `r`), а не пересматривать всю историю пользователя. Кроме
общего ядра выполните пункт для своего языка:

Python - нельзя использовать `collections.deque` и `list.pop(0)`. Своя очередь на `list` с индексом головы и периодическим сжатием; в комментарии обоснуйте, почему сжатие даёт амортизированное O(1)
---

## Идея
Для каждого пользователя заводим **список очередей** — по одной на каждое
правило (так как у разных правил разные окна `w`)
Запрос, который ещё «жив» для правила `(10, 1000)`, может уже выйти из окна
для правила `(1, 3)`.

Каждая очередь хранит **пропущенные** времена. Отклонённые запросы не
добавляются — иначе они бы «продлевали бан» и учитывались в следующих окнах,
что противоречит условию.

Пользователи хранятся в `dict`, а не в массиве, потому что `dict` хранит только тех, кто реально встретился.

### Структура `UserQueue`

Своя очередь на `list` с индексом головы `first_index`:
`self.data` - список времён, когда запросы были пропущены.
`self.first_index` - индекс первого живого элемента в data
(мы не удаляем элементы из data физически, вместо этого двигаем first_index вправо. всё, что левее first_index, — мёртвое (вышло из окна). всё, что правее или равно — живое)

- `remove_firsts_index` - двигает first_index вправо, пока не дойдёт до живого элемента. (это амортизированное O(1): каждый элемент сдвигает first_index ровно один раз за всю жизнь. Суммарно по всем вызовам — не больше n итераций. Значит, в среднем на запрос — O(1).)

- `collections.deque` и `list.pop(0)` по условию задачи они
запрещены. Кроме того, `list.pop(0)` сдвигает все элементы влево — это O(n)
на каждое удаление, что не даёт амортизированного O(1).

- dikt_queue — словарь user_id → список UserQueue. Для каждого пользователя — свой список очередей (по одной на правило).

- result — список символов A/D. В конце склеим в строку

### Амортизированное O(1)

Каждый запрос добавляется в очередь **один раз** и удаляется из неё **один
раз**. Суммарно удалений — не больше `n`. Даже если в одном запросе
удалится сразу много элементов, в среднем на запрос — O(1).

### Код

```python
import sys
import json


class UserQueue:
    "очередь пропущенных времен для одного пользователя"
    def __init__(self):
        self.data = []
        self.first_index = 0

    def add(self, time: int):
        "время в конец"
        self.data.append(time)

    def remove_firsts_index(self, time: int):
        "удалить из начала времена"
        while self.first_index < len(self.data) and self.data[self.first_index] <= time:
            self.first_index += 1

    def size(self):
        "кол-во эл в очереди"
        return len(self.data) - self.first_index

def solve(rules: list[list[int]], users: list[int], times: list[int]) -> str:
    # храним ключём номер пользователя а значением его очередь
    dikt_queue = {} # для каждого пользователя — свой список очередей (по одной на правило)
    result = [] # список символов A/D
    for u, t in zip(users, times):
        if u not in dikt_queue: # если пользователь u встретился впервые создаём для него пустой список
            dikt_queue[u] = []

            for _ in rules: #не важно значение, просто повтори len(rules) раз. У нас 1–3 правила, значит 1–3 очереди
                dikt_queue[u].append(UserQueue())
        queues = dikt_queue[u] # список очередей для этого пользователя (длина = число правил)
        i = 0 # индекс текущей очереди
        allowed = True
        for r1 in rules:
            k, w = r1 # распаковываем правило [k, w] в две переменные
            # достаём нужную очередь под это правило
            queue = queues[i]
            queue.remove_firsts_index(t - w)
            if queue.size() >= k: # если живых элементов стало >= k, правило нарушено
                allowed = False
            i += 1 # к следующему правилу
        if allowed:
            result.append("A")
            for q in queues:
                q.add(t)
        else:
            result.append("D")
    return "".join(result)


def main() -> None:
    obj = json.loads(sys.stdin.readline())
    sys.stdout.write(json.dumps(solve(obj["rules"], obj["users"], obj["times"])))


if __name__ == "__main__":
    main()
```

### Как это работает по шагам

1. `dikt_queue` — словарь `user_id → список UserQueue` (по одной на правило).
2. Для каждого запроса `(u, t)`:
   - если пользователь новый, создаём для него список очередей;
   - для каждого правила `(k, w)`:
     - берём очередь под это правило;
     - `remove_firsts_index(t - w)` — убираем всё, что вышло из окна
       `(t - w, t]`;
     - если `size() >= k` — правило нарушено;
   - если все правила ок → `A`, добавляем `t` во **все** очереди пользователя;
   - иначе → `D`, не добавляем ничего.
3. Возвращаем строку из `A`/`D`.

## Вопросы на защите

1. Почему решение работает за амортизированное O(1), если в одном запросе
   из очереди может удалиться сразу много элементов?
- потому что каждый элемент удаляется из очереди ровно один раз за всё
время работы. Суммарное количество удалений по всем запросам не превышает
`n` (число запросов).

2. Что изменится, если отклонённые запросы тоже будут учитываться?
- отклонённый запрос продлевал бы бан. пользователь, которого
отклонили, всё равно занимал бы место в окне 
(пользователь, которого отклонили,
всё равно не смог бы отправить следующий запрос в течение секунды)

3. Пользователей 10⁹ возможных, а активных мало: почему здесь хэш-таблица, а не
   массив, и когда было бы наоборот?
- хэш-таблица (`dict` в python) хранит только тех пользователей, которые
реально встретились 
(активных 1000, то памяти уйдёт на 1000
записей, а не на 10⁹. массив на 10⁹ гигабайты памяти, которые
избыточны)

- массив был бы лучше, если бы ID пользователей были плотными (0..n) и их было
немного. Тогда доступ по индексу — O(1) без хэширования, и памяти уходит
ровно `n` ячеек.

4. Память растёт с числом пользователей, даже неактивных. Как бы вы её
   ограничили? (Подсказка: вспомните LRU с практики.)          
**LRU-кэш** (Least Recently Used) - наименее недавно использованный
- LRU-кэш (Least Recently Used): хранить не всех
пользователей, а только последние `M` активных. Когда приходит новый
пользователь, а кэш заполнен, удаляем того, кто дольше всех не активен.
